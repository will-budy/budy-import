# Generated SDK Clients & OpenAPI Pipeline

Hindsight exposes its dataplane API (`hindsight-api-slim`, a FastAPI app) to Python, TypeScript, Rust, and Go consumers through auto-generated client SDKs. Rather than hand-writing four HTTP clients, the project treats the FastAPI app's own OpenAPI schema as the single source of truth and regenerates each SDK's low-level transport layer from it. This page explains how the spec is produced, how each of the four generators consumes it, what hand-maintained code survives regeneration, and the CI gate that keeps all of it in sync after an endpoint change.

## Pipeline Overview

```text
FastAPI app (hindsight-api-slim)
        │  app.openapi()
        ▼
scripts/generate-openapi.sh
        │  uv run generate-openapi  (hindsight-dev/hindsight_dev/generate_openapi.py)
        ▼
hindsight-docs/static/openapi.json   ← single source of truth for all 4 SDKs
        │
        ├─▶ scripts/generate-clients.sh ──▶ Python  (openapi-generator, Docker)
        │                               ├─▶ TypeScript (@hey-api/openapi-ts)
        │                               └─▶ Go       (openapi-generator, Docker)
        │
        └─▶ hindsight-clients/rust/build.rs ──▶ Rust (progenitor, build-time)
```

The spec is generated once (`scripts/generate-openapi.sh`) and written to `hindsight-docs/static/openapi.json`, which every downstream generator reads directly or indirectly. Three of the four SDKs (Python, TypeScript, Go) are regenerated by an explicit script; the Rust client instead regenerates itself from the same file during every `cargo build`.

## Step 1: Regenerating the OpenAPI Spec

`scripts/generate-openapi.sh` runs `uv run generate-openapi` from `hindsight-dev`, which is a console-script entry point (`generate-openapi = "hindsight_dev.generate_openapi:generate_openapi_spec"`) that instantiates a mock `MemoryEngine` (`db_url="mock"`, `ollama` provider with dummy credentials — no real backend needed), wraps it with `create_app(_memory)`, and dumps `app.openapi()` to `hindsight-docs/static/openapi.json`.

```python
# hindsight-dev/hindsight_dev/generate_openapi.py:50-68
_memory = MemoryEngine(
    db_url="mock",
    memory_llm_provider="ollama",
    memory_llm_api_key="mock",
    memory_llm_model="mock",
)
app = create_app(_memory)
openapi_schema = app.openapi()
_restore_binary_format(openapi_schema)
...
json.dump(openapi_schema, f, indent=2)
```

One notable transform runs before the file is written: `_restore_binary_format` rewrites OpenAPI 3.1 binary-upload fields (`{"type": "string", "contentMediaType": "application/octet-stream"}`, which is what modern FastAPI/Pydantic emit) back into the OpenAPI 3.0-style `format: binary`. This exists because `openapi-generator` v7.10.0 (used for the Python and Go clients) doesn't recognize `contentMediaType` and would otherwise silently generate the `files` upload parameter as a plain string instead of a binary multipart field, breaking file-upload endpoints in every generated client that isn't Rust.

After the JSON is written, `scripts/generate-openapi.sh` also runs `npm run build` in `hindsight-docs` so the Docusaurus site's API reference stays in sync.

## Step 2: Generating the Four Clients

`scripts/generate-clients.sh` pins `OPENAPI_GENERATOR_VERSION="v7.10.0"` for reproducibility and drives three of the four SDKs from `hindsight-docs/static/openapi.json`; it explicitly notes that the Rust client is generated separately, at build time.

### Per-language generation

| Language | Generator | Trigger | Docker required |
|---|---|---|---|
| Rust | `progenitor` (build-dependency) | `cargo build` via `build.rs` | No |
| Python | `openapi-generator-cli:v7.10.0`, `-g python` | `./scripts/generate-clients.sh` | Yes |
| TypeScript | `@hey-api/openapi-ts` (`npm run generate`) | `./scripts/generate-clients.sh` | No |
| Go | `openapi-generator-cli:v7.10.0`, `-g go` | `./scripts/generate-clients.sh` | Yes |

The script's own banner claims the Go client uses `ogen`, but the actual `docker run` invocation targets the `go` generator inside `openapitools/openapi-generator-cli`, the same tool used for Python — the banner text is stale relative to the implementation.

**Rust** (`hindsight-clients/rust/build.rs`) is the odd one out: it has no shell step in `generate-clients.sh` at all. Every `cargo build` reads `hindsight-docs/static/openapi.json` directly (`cargo:rerun-if-changed` is set on that path), performs several spec transforms in-memory, and hands the result to `progenitor::Generator`:
1. Downgrades `openapi: "3.1.x"` to `"3.0.3"` and converts `anyOf`-with-`null` into `nullable: true` (progenitor targets OpenAPI 3.0 via the `openapiv3` crate).
2. Collapses `anyOf` unions where every member is a plain string (e.g. a `date-time`-formatted string alongside a plain string) into a single `{"type": "string"}`, avoiding a progenitor bug that emits an unserializable `#[serde(flatten)]` over a primitive.
3. Filters out every path containing a `multipart/form-data` request body, since progenitor doesn't support multipart — meaning **file-upload endpoints are absent from the generated Rust client** by design.
4. Patches a progenitor codegen bug where optional header parameters call `.to_string()` on an `Option<&str>` directly.

The generated code is written to `OUT_DIR/hindsight_client_generated.rs` and pulled into `hindsight-clients/rust/src/lib.rs` via `include!(concat!(env!("OUT_DIR"), ...))`.

**Python** (`hindsight-clients/python`) generates into a temporary directory first, not directly into the working tree — Docker Desktop on macOS was silently dropping supporting-file writes (`api_client.py`, `configuration.py`, README) when the output volume was bind-mounted directly, so the script generates to `mktemp -d`, verifies `api_client.py` exists, then `cp -R`s the result into place. Generation is driven by `hindsight-clients/python/openapi-generator-config.yaml` (`packageName: hindsight_client_api`, `library: asyncio`, docs/tests disabled). Two manual patches follow generation:
- `rest.py`'s `RESTClientObject.__init__` is rewritten to defer `aiohttp.TCPConnector`/`ClientSession` creation until the first request, because building it eagerly in `__init__` requires a running event loop that doesn't exist yet at client-construction time.
- `py.typed` marker files are (re)created in both `hindsight_client_api/` and `hindsight_client/` for PEP 561 type-checker support.

**TypeScript** (`hindsight-clients/typescript`) is regenerated with `npm run generate`, which runs `npx @hey-api/openapi-ts` against the config in `openapi-ts.config.ts` (`client: "@hey-api/client-fetch"`, input `../../hindsight-docs/static/openapi.json`, output `./generated`, plugins `@hey-api/typescript` + `@hey-api/sdk`). One post-generation patch is applied to `generated/client/client.gen.ts`: it destructures out the internal `client` field from `opts` before spreading into `RequestInit`, because Deno's `Request` constructor rejects a `client` key (it collides with `Deno.HttpClient`'s reserved option name).

**Go** (`hindsight-clients/go`) is generated via `openapi-generator-config.yaml` (`generatorName: go`, `packageName: hindsight`, `isGoSubmodule: true`). Before generation the script preserves `README.md`, `integration_test.go`, `null_test.go`, `trace_test.go`, and `hindsight_client.go` in a temp dir; after generation it deletes generator boilerplate (`docs/`, `git_push.sh`, `.travis.yml`, etc.), restores the preserved files, and applies one known-bug patch: `api_files.go` uses `os.File` but the generator sometimes omits the `"os"` import, so the script `sed`s it back in. It finishes with `go mod tidy && go build ./...` to verify the module compiles.

## Generated vs. Maintained Code

Every client separates auto-generated transport code from a small, hand-written convenience layer that the generation scripts are careful to preserve:

| Language | Generated (overwritten every run) | Maintained (preserved across runs) |
|---|---|---|
| Python | `hindsight_client_api/` (api_client, models, `banks_api`, `memory_api`, etc.) | `hindsight_client/hindsight_client.py`, `README.md`, `pyproject.toml`, `tests/` |
| TypeScript | `generated/` (`client.gen.ts`, `sdk.gen.ts`, `types.gen.ts`) | `src/index.ts`, `package.json`, `tests/` |
| Go | `api_*.go`, `model_*.go`, `client.go`, `configuration.go` | `hindsight_client.go`, `README.md`, `integration_test.go`, `null_test.go`, `trace_test.go` |
| Rust | `OUT_DIR/hindsight_client_generated.rs` (build artifact, not committed) | `src/lib.rs`, `Cargo.toml` |

The maintained wrappers exist to give each SDK a friendlier surface than raw generated operations. For example, `hindsight_client/hindsight_client.py` is explicitly documented as "MAINTAINED and NOT auto-generated," importing the generated `banks_api`, `memory_api`, etc. and layering a Pythonic API on top; the Go equivalent, `hindsight_client.go`, adds `NewAPIClientWithToken`/`NewAPIClientWithTimeout` constructors and a version-aware `DefaultUserAgent`; the Rust `lib.rs` re-exports the generated types via `include!` and adds `CLIENT_VERSION`/`DEFAULT_USER_AGENT` constants plus a `reqwest_client_with_user_agent` helper.

Because the wrapper layers are hand-written, they can drift from the spec independently of the generated code. `hindsight-dev/hindsight_dev/client_coverage_check.py` (`uv run client-coverage-check`) guards against this: it scans the Python and TypeScript wrappers for SDK call sites (e.g. `sdk.recallMemories(` / `self._memory_api.recall_memories(`) and verifies every OpenAPI request-body field appears near that call site, with snake_case/camelCase normalization and a per-client `.openapi-coverage.toml` escape hatch for deliberate omissions.

## CI Enforcement: `verify-generated-files`

The `verify-generated-files` job in `.github/workflows/test.yml` is the mechanism that actually keeps all of this current — it doesn't trust that a contributor remembered to regenerate anything. On every run it checks out the PR head, installs Python/Node/Rust toolchains, and executes the full generation chain in order:

```yaml
# .github/workflows/test.yml:4768-4800
- name: Run generate-openapi
  run: ./scripts/generate-openapi.sh
- name: Run generate-bank-template-schema
  run: ./scripts/generate-bank-template-schema.sh
- name: Run generate-clients
  run: ./scripts/generate-clients.sh
- name: Run generate-docs-skill
  run: ./scripts/generate-docs-skill.sh
- name: Run lint
  run: ./scripts/hooks/lint.sh
- name: Verify no uncommitted changes
  run: |
    if [ -n "$(git status --porcelain)" ]; then
      echo "❌ Error: Generated files are out of sync with committed files."
      ...
      exit 1
    fi
```

If regeneration produces any diff against what's committed, the job fails and prints the exact four commands (plus `lint.sh`) a contributor must run locally before pushing. This is the practical answer to "what do I do after changing an endpoint": modify the FastAPI route/schema, then run `./scripts/generate-openapi.sh && ./scripts/generate-clients.sh`, build `hindsight-cli`/`hindsight-clients/rust` to pick up the Rust regeneration, and commit the resulting diff across `hindsight-docs/static/openapi.json` and all four `hindsight-clients/*` directories together.

## Workflow After an Endpoint Change

```text
1. Edit FastAPI route/schema in hindsight-api-slim/hindsight_api/api/http.py (or models)
2. ./scripts/generate-openapi.sh        → hindsight-docs/static/openapi.json updated
3. ./scripts/generate-clients.sh        → Python + TypeScript + Go regenerated
4. cargo build (hindsight-clients/rust) → Rust regenerated via build.rs
5. If the change touches a request-body field consumed by hand-written wrappers:
     update hindsight_client/hindsight_client.py, src/index.ts, hindsight_client.go
     uv run client-coverage-check   (hindsight-dev) to confirm coverage
6. ./scripts/hooks/lint.sh
7. git diff --stat / git status — commit every touched generated + maintained file together
```

This is the same sequence CI runs via `verify-generated-files`; running it locally before opening a PR avoids the CI failure loop entirely.

Nothing in this pipeline is tied to a specific model provider, hosted service, or proprietary connector — the OpenAPI spec is produced entirely from the FastAPI app's own schema with a mocked `MemoryEngine`, and all four generators (`progenitor`, `openapi-generator`, `@hey-api/openapi-ts`) run against that static JSON file locally or via pinned Docker images, independent of which LLM/embeddings/reranker backend a given Hindsight deployment is configured with.
