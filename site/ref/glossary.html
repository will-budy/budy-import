    Temporal Nexus Service¶

    A Temporal Nexus Service is a service contract built on top of Temporal that exposes durable, distributed operations as callable endpoints — conceptually similar to a REST API, but built for work that is async, long-running, or needs to survive failures.

    Where a REST API call is transient (the caller either gets a response or handles a timeout on its own), a Nexus call is durable: if the caller or the service crashes mid-operation, Temporal ensures the work resumes from where it left off. The caller does not need to know whether the underlying implementation is a short-lived function or a multi-day workflow — it just calls the endpoint and Temporal handles the rest.

    Why we use it: Almost all services in the de-v2 platform are Temporal workers. Nexus lets those services expose clean, typed contracts to each other without giving up the durability and observability guarantees that Temporal provides. It is our preferred internal service contract wherever REST is not strictly required (e.g., REST remains necessary for inbound webhooks and external-facing APIs).

    Example: The Context Service needs to request an LLM review of a proposed memory update before approving it. Rather than making a REST call to the LLM Service — which would be lost if anything crashed mid-review — the Context Service calls the LLM Service's Nexus endpoint. Temporal tracks the in-progress call. If the LLM Service worker restarts during the request, Temporal retries from the last checkpoint. The Context Service does not need to implement its own retry logic or dead-letter queue. Temporal handles it, and the full operation is visible in the Temporal UI from start to finish.

    Further reading: Temporal Nexus documentation

    Dynamo worker¶

    A Dynamo worker is a Temporal worker, one per digital teammate (DT) workbench, that runs the DT's deterministic workflows. Those workflows may contain prompts and call external and internal systems. Each DT's worker has its own repository in GitLab (gitjib-cluster-1), created from a template; once an image built to the required spec is pushed, nainai-cluster-1 deploys it. dt-consulting-services-1 is how a DT gets a workflow added or changed.

    Engagement¶

    An engagement is a digital teammate's request to dt-consulting-services-1 to add or change a workflow of its Dynamo worker. It is written like a PRD (outcome, context, audience, do's and don'ts, success criteria, references to existing resources) and carries no implementation detail. A DT has at most one live engagement. It is done when the workflow is published and the new worker version is healthy.

    Sandbox¶

    A sandbox is an isolated workspace that Karkhana (karkhana-cluster-1) runs for a caller in the caller's tenant namespace: one pod with a persistent workspace volume and its own ServiceAccount, created from a SandboxType. Pausing deletes the pod and keeps the volume; resuming starts a new pod. Desired state is a row in Postgres written by sandbox-manager-1; sandbox-operator-1 makes Kubernetes match it. Design: Karkhana sandboxes.

    SandboxType¶

    A SandboxType is the cluster-scoped custom resource (karkhana.budy/v1alpha1) that is the catalog of what a sandbox can be: image, workspace volume, resources, lifetime limits, placement, network profile, secrets, the identity it gets, the roles allowed to request it (allowedRoles) and per-tenant and per-requester limits. Example: claude-coder-1.

    Workload session¶

    A workload session is a short-lived platform identity that a platform service creates in authz-manager-1 for one workload it runs on a tenant's behalf, such as a sandbox. It is a user homed on the tenant, with the workload's ServiceAccount as its only identity and the roles a reviewed configuration allows, until an expiry. It is released when the work stops and ends by itself otherwise. Standard: Component Authorization Module Standard.

    glassboxId¶

    glassboxId is the claim in a tenant STS session that names the billing entity: the entity that pays for what the session does, either the tenant or a digital teammate of it. STS decides it and a caller cannot set it; a workload session has its entity fixed when it is created. Services record it with their usage and never derive it. See the Usage Metering Standard and the authorization standard.

    Network profile¶

    A network profile is a named set of allowed network destinations for pods that a platform operator creates in tenant namespaces. It is one cluster-wide Cilium policy, selected by the pod label budybot.io/netpol: <profile> in namespaces managed by a UserOrg, and the label is reserved by admission policy. Example: sandbox-coder-1. A SandboxType names its profile in networkProfile. See Network Policy & mTLS.
